# LESSONS — 001-cli

## L1 playground 模板没有表格样式

- 现象：照模板填入 `<table>` 后渲染成无边框、无表头底色的裸表格
- 根因：sdd 的 playground 模板只为 Kanban、chips、fold 等组件写了样式，没有通用表格样式
- 规避：本档案在 `<style>` 末尾补了 `main table/th/td`；S6 自我升级时把它回补进 skill 模板

## L2 playground 的 `<pre>` 里不能出现 `-->`

- 现象：`gen_kanban.py --check` 报「HTML 注释开闭不配平」
- 根因：ASCII 箭头 `-->` 与 HTML 注释结束符相同，检查脚本按字面计数
- 规避：箭头一律写 `─→` 或 `→`；命令行参数里的 `--` 写成 `&#45;&#45;`

## L3 `gen_kanban.py --check` 不比对依赖列

- 现象：PLAN 里 T3.1 的依赖改成 `T1.2,T2.1`，playground 仍是 `T1.2`，`--check` 报 OK
- 根因：一致性检查只比对 id、状态、分列，不比对 `dep`
- 规避：改依赖时手工同步 playground；S6 自我升级时让 `--check` 也比对 `dep` 和 `ac`

## L4 并发测试过一次不算证据

- 现象：T1.1 首次实施时 `concurrent_hooks_no_lost_writes` 本地过了一次，就报了「400 次写入零丢失」；独立评审复跑，debug 下 4 次失败 3 次
- 根因：首次打开时切 WAL 需要排他锁，而且不受 busy_timeout 约束，并发首开会立即返回 BUSY；是否触发取决于调度时机
- 规避：并发、时序类验收一律连跑多次（本仓定为 debug 与 release 各 10 次）；报告里写「N/N 通过」，不写「通过」

## L5 进程层面的事实要实测，不能靠推断

- 现象：设计按「只有 /exit 算关闭」推演，漏掉了 `claude -p`（F10）和会话内 `/resume`（F11）两种真实事件序列，二者都会造成误恢复
- 规避：凡是「哪些事件会发生」的判断，先在独立 tmux socket 上用真实 claude 跑一遍再写进状态机；探针脚本见 `notes/hook-probe.md` 的方法节

## L6 修复会带入新的回归，修复轮也要独立复核

- 现象：T1.1 第 1 轮的 9 项修复里，`touch_and_repair` 与「一进程一槽位」各带入一个会让活会话被重复恢复的回归（评审 R1、R2）
- 根因：修复只对着本轮发现写测试，没有回到「两个进程共用会话」「身份信息缺失」这两个维度去扫
- 规避：涉及身份判定的修复，凡是放宽匹配的地方都要问一句「信息缺失时会不会误判」；修复轮照样派复核，变异要覆盖每一道新加的保护（本轮就有一道保护的变异起初没有变红）

## L7 verify 命令要原样跑一遍

- 现象：两条 `verify:` 把多个测试名直接接在 `cargo test` 后面，cargo 只收一个位置参数，命令本身报用法错误
- 规避：收尾前用脚本把 spec 里的每条 `verify:` 原样执行（`rg -o 'verify: \`…\`'` 提取后逐条 `bash -c`）；多个过滤器写在 `--` 之后

## L8 `git checkout <branch> -- <dir>` 不会删除分支里已删掉的文件

- 现象：squash 回 main 时用 `git checkout feature -- .sdd`，main 上残留了分支里已经 `git mv` 走的旧路径文件，树校验 `git diff --quiet feature main` 失败
- 规避：squash 后必须做树校验；按目录取内容时用 `git restore --source=<branch> --staged --worktree -- <dir>`（会同步删除），或直接 `git read-tree` 整树

## L9 「防重复」不能靠计时器，要靠被保护对象本身的状态

- 现象：T1.4 首版用「60 秒内发起过恢复」防重复恢复；评审复现：被拉起的进程超过 60 秒没上报，或 tmux 慢于超时被误判失败，都会再拉一份
- 根因：计时器只是在猜被拉起的进程还在不在；真实状态（pid 是否存活）明明拿得到
- 规避：拉起子进程的地方当场记下它的身份（pid + 启动时间 + 位置），之后一律按存活判定；计时器只兜底「身份没拿到」的情况。超时这类不确定的失败，先去确认结果再决定回滚

## L10 用户真实文件的预览要在交付前看一眼

- 现象：T2.1 的 zsh 区块在临时文件上测得都对，用真实 `~/.zshrc` 做 `setup --dry-run` 才发现它插进了另一个工具的受管区块里（starship 那行在别人的区块内），下次那个工具同步就会把它冲掉
- 规避：会写用户真实文件的功能，合入前对真实文件跑一次 dry-run 看 diff；夹具要包含「目标行在别人的受管区块里」这种真实形状

## L11 私有词扫描不能每次手写，更不能为了「过」而收窄

- 现象：T2.2 起测试夹具用了真实主机名、工作区名和供应商名；当时的扫描命令为了排除「看起来是业务词」的命中被手工收窄，于是放过了它们，并已推到远端（私有仓，尚未公开）
- 根因：词表散落在每次手写的命令里；收窄排除项时没有逐条看命中位置
- 规避：词表固定放在仓外（`~/.config/cc-moss-dev/private-words.txt`，词表本身就含私有名，不能入公开仓），统一用 `git grep -i -E -f <词表>` 扫描，命中一律修正而不是排除；测试夹具只用中性名字（host-a、api-gw、acme）；公开前扫描全部历史

## L12 界面验收要看「整屏」，不能只看单个元素对不对

- 现象：T2.2、T2.3 各项单测都过、截图上每个元素都「对」，用户一眼看过去却是「一大片、眼睛看花」
- 根因：每轮都在原结构上加信息（两行、路径、标签、零计数），没有退一步问「这一屏让人先看到什么」；相同信息每行重复
- 规避：界面类任务先列「这一屏要回答的唯一问题」（这里是：我要回哪个会话）；重复信息上提为分组标题、细节只给选中项、零值不画；交付前用真实形状的数据截整屏图自己看一遍

## L13 测试里任何会执行外部安装的路径，都要由环境变量从根上关掉

- 现象：T3.1 首轮 e2e 里，`install --yes --with aliases` 在桩环境中真的执行了 `brew install eza bat fd`；只因测试 PATH 里没有 brew 才没装成
- 根因：测试只隔离了 HOME 和配置文件，没想到 `--yes` 会把「询问后安装」变成直接执行；平台检测拿的是真机平台
- 规避：会调用包管理器、网络安装脚本的命令，测试辅助函数一律设置 `CC_MOSS_PLATFORM=other`（不生成任何安装命令）；
  需要验证命令内容的用例只用 `--dry-run`，并显式指定平台

## L14 装机类功能要在干净设备上跑一遍，桩测试替代不了

- 现象：T3.1 的 10 个桩 e2e 全绿，第一次在 Docker 里的全新 Ubuntu 上跑就失败两次：没有 apt 包索引时 `apt-get install` 找不到包；新用户没有 `~/.local/bin`，starship 官方脚本拒绝安装
- 根因：桩环境只证明「cc-moss 会生成哪些命令」，证明不了「这些命令在新机器上能成功」；开发机早已具备这两个前提
- 规避：`scripts/clean-room.sh` 在全新容器里用真实包管理器跑 install → doctor → 再 install；凡改动安装命令或资产都要过一遍。
  本地负载高时借空闲机器跑（SSH 会话里 Docker 拉镜像会被钥匙串凭据助手卡住：用只含 docker 的 PATH 和空的 DOCKER_CONFIG）

## L15 隔离测试要连 ZDOTDIR 一起隔离；不同工具的备份不能共用命名

- 现象：手工验证迁移脚本时只把 HOME 指向临时目录，脚本却读了真实的 `~/.zshrc`：当前 shell 环境里 `ZDOTDIR` 被设成了真实家目录（因为已迁移完，未改动任何东西）。
  另外，本机切换时迁移脚本和私有同步脚本在同一秒各写了一份 `.bak-<秒级时间戳>` 备份，后者覆盖了前者
- 根因：只按「HOME 决定一切」去隔离；两个工具各自假设备份名独一无二
- 规避：任何读写 dotfiles 的验证都同时设置 `HOME` 和 `ZDOTDIR`（cc-moss 的测试 helper 已清除 ZDOTDIR）；
  每个工具的备份带自己的前缀（`.cc-moss-*`、`.bak-migrate-*`、`.bak-block-*`），并且遇到同名绝不覆盖
