## 目标

用户 `brew install` 一条命令就同时拿到 CLI 与状态栏 App；`cc-moss install` 问一句后把 App 放进 `~/Applications`（通知只在「应用程序」目录里可用）；`cc-moss update` 升级 CLI 时 App 跟着升，原本开着的 App 自动重启；`cc-moss doctor` 告诉你 App 在不在、版本对不对、放的位置能不能收通知。CLI 与 App 永远同一个版本号、同一个 Release。

## Scope（YAGNI）

**In**
- `apps/macos/scripts/bundle.sh`：版本号取自 workspace `Cargo.toml`（已有），补 App 图标（`AppIcon.icns`，由 `docs/assets/icon.svg` 生成并入仓，附重新生成脚本）；输出固定在 `apps/macos/build/cc-moss.app`；新增 `scripts/check-bundle.sh` 校验 Info.plist 版本 = Cargo 版本、`LSUIElement`、图标、ad-hoc 签名有效
- `release.yml`：两个 macOS 目标各自构建对应架构的 App（`--arch arm64` / `--arch x86_64`），把 `cc-moss.app` 放进同一个 tarball、与二进制并列；Linux tarball 不变；校验和照旧；`workflow_dispatch` 的 dry run（输入 `ref`）照常可用，并在 dry run 里额外渲染一次 Homebrew 公式做语法检查
- Homebrew 公式模板：macOS 上 `prefix.install "cc-moss.app"`；caveats 提示运行 `cc-moss install`；Linux 不变；渲染逻辑抽成 `packaging/homebrew/render.sh`，发布与 dry run 共用
- `cc-moss install`：新增部分 `app`（可 `--skip app`）。macOS 上在二进制旁边或 Homebrew keg 里找到随附的 App 时，说明并询问（遵守 `--yes` / 非交互即拒绝的既有约定，`--dry-run` 只说不做），复制（不是符号链接）到 `~/Applications/cc-moss.app`；已有同版本则不动，版本不同才替换；替换时 App 在运行就先礼貌退出、换好后 `open -g` 重新打开
- `cc-moss update`：CLI 升级成功后，若 `~/Applications/cc-moss.app` 存在且新随附 App 版本不同，替换并（若在运行）重启。Homebrew 从新 keg 取，Release 下载从同一个 tarball 取；cargo 安装没有随附 App，只提示。退出用 `osascript … to quit`，等待后 `open -g`，绝不 `pkill cc-moss`
- `cc-moss doctor`：macOS 上加一行「状态栏 App」：在不在、版本、是否与 CLI 一致、是否在「应用程序」目录
- 测试全部用临时 HOME 与假 App（只有 Info.plist 与一个脚本），`osascript`/`pgrep`/`open` 用 PATH 上的桩；不碰真实 `~/Applications`，不启动真 App
- 文档：`docs/guide.md`、`docs/guide.en.md` 安装 / 升级 / 卸载；`CHANGELOG.md` Unreleased

**Out**
- 公证、Developer ID、Homebrew cask（A12：办了开发者账号再加）
- universal 二进制（按架构分包即可，tarball 本来就分架构）
- `install --uninstall` 删除 `~/Applications/cc-moss.app`（见 deliberately_skipped）
  - AMEND 2026-10-17（用户决定）：改为 In。`install --uninstall` 在 macOS 上退出并删除 bundle id 为本项目的 `~/Applications/cc-moss.app`（符号链接只删链接）与 `~/Library/LaunchAgents/io.github.larrykoo711.cc-moss.login.plist`，单独询问，遵守 `--dry-run`/`--yes`；不是我们的 App 保留并提示
- 首次启动引导（T4.2）

## 风险与回退

- Homebrew 改动 keg 里的 Mach-O 会使签名失效：App 只链接系统库，brew 不会改；若改了，Apple 芯片上 brew 会重新 ad-hoc 签名。dry run 后 `codesign --verify` 把关
- macOS tar 夹带 `._*` 元数据文件：打包时 `COPYFILE_DISABLE=1`
- 升级时误杀 CLI：只用 bundle id 退出 App，进程判断用 App 内可执行文件的完整路径，绝不 `pkill cc-moss`
- 替换中途失败：先复制到同目录临时名，再删旧、改名；失败只警告，不影响已完成的 CLI 升级
  - AMEND 2026-10-17（评审）：改为旧 App 改名为同目录备份名 → 新 App 改名到位 → 删备份；任一步失败即还原备份、删临时副本，原本在运行的旧 App 重新打开。承诺：失败时旧 App 完好、不留 `.cc-moss.app.*`
- 回退：`--skip app`；App 可直接拖进废纸篓；release.yml 的 App 步骤只在 macOS 目标上运行，删掉即回到旧包

## Notes / 开放问题 / 澄清日志

- 2026-10-17 派单要求 `risk: release`，gate 词表无此项，取 `migration`（独立评审档），理由见 frontmatter 注释
- 测试用的假 App 位置覆盖：`CC_MOSS_BUNDLED_APP` 只在 debug 构建生效（与 `CC_MOSS_UPDATE_EXE` 同理），发布构建不会被环境变量引去复制别的目录
- 2026-10-17 评审修复（分支 `feature/002-t4.1-fixes`）：
  - sudo/root（euid 0 或设了 `SUDO_USER`）下 `install` 与 `update` 都不碰 `~/Applications/cc-moss.app`（不复制、不退出、不启动），只提示一行「不加 sudo 运行 `cc-moss install`」；`--uninstall` 同理
  - 退出 App：先 `osascript`；失败（如自动化权限被拒）则对锚定的 `pgrep -f <完整可执行路径>` 找到的 PID 逐个发 SIGTERM，绝不按名字；`install` 里 App 这一步失败（含退出超时）只警告，后续步骤照跑；只有「无终端又没 `--yes`」的拒绝仍是错误
  - 版本按 semver 比较（预发布早于正式版）：已装的更新则不降级（`update` 提示一行，`install` 说明后跳过，`--yes` 也不降级）；`dev` 或无法解析的版本视为未知，一律不动
  - 找不到随附 App 时 `install` 提示一行去哪拿（解压目录里 `./cc-moss install` 或拖进「应用程序」）；`update` 的手动升级说明也提到 App
  - 测试新增覆盖：`CC_MOSS_SYSTEM_APPLICATIONS` 代替 `/Applications`、`CC_MOSS_APP_QUIT_TIMEOUT_MS` 缩短退出等待，都只在 debug 构建生效；测试默认去掉 `SUDO_USER`
  - `bundle.sh`：`CFBundleVersion` 只取 `-` 之前的数字部分，`CFBundleShortVersionString` 保留完整版本；`check-bundle.sh` 分别校验
  - `release.yml`：`check` 任务在打 tag 时也跑，`publish` 依赖 `[build, check]`；dry run 依旧不发布
  - `install --uninstall` 不支持 `--skip`（clap 冲突），所以保留 App 靠单独那一问答「否」
