## Changes

### 用户可见

- 普通重开与「应用渠道模型」分开；明确应用当前设置中的目标模型，保留原会话，不重发上一条任务。
  普通忙碌会话可排队，执行前读取最新设置，尚未开始时可取消。
- 明确 API 错误单独提示，与配置变化提醒区分；不反复建议应用同一个失败模型，不偷偷试用其他模型。
- 重开和明确确认后的窗格重建，都先确认原进程退出；信号失败、状态未知、退出超时便停止，避免第二份会话。
- 恢复操作只有一份进度和结果；技术详情默认折叠，排队原因如实显示，迟到结果不污染另一个会话。
  只交出命令仍是等待确认，不当作已经恢复，更不当作 API 已可用。

### 内部与边界

- 配置来源校验、排队占有与代次释放、API 错误增量扫描、退出后身份复核，以及跨会话 UI 请求绑定。
- PTY 转发集成的窗格重建仅限空闲时单独确认；会结束该窗格终端集成及其他任务，不复用普通重开的授权。
- 不承诺任意模型或生产渠道可用，不自动修复历史 orphan 进程或错配登记，不自动重发任务。
- 详细范围与证据见 `.sdd/004-moss-agent/reports/provider-delivery.md`（F42–F51），
  以及 `docs/guide.md` / `docs/guide.en.md` 的渠道切换和窗格重建章节。

## Release procedure

**以下均为待执行步骤，不是执行日志。提交、推送 main、打 tag、GitHub Release、部署和安装须由 controller 按各自授权处理。**

1. 在最终版本树上检查 `git diff --check` 与锁文件差异；锁文件只能改变两个工作区包的版本。
   留存最终 commit/tree，然后按 CI 执行并记录结果：

   ```sh
   cargo fmt --all --check
   cargo clippy --all-targets --locked -- -D warnings
   cargo test --all --locked -- --test-threads=4
   apps/macos/scripts/swift.sh build
   apps/macos/scripts/swift.sh test
   apps/macos/scripts/bundle.sh
   apps/macos/scripts/check-bundle.sh
   pnpm --dir site build
   pnpm --dir site test
   ```

   Rust 全量覆盖 Linux/macOS；另完成 CI 的 MSRV、shell 语法与 Homebrew formula 检查。
   Linux 聊天测试环境先检查 `perl -MTime::HiRes -MPOSIX -e 'exit 0'`，避免把镜像缺依赖误判为产品失败。
   CI 使用 pnpm 10；本机 pnpm 11 若自动要求重装依赖，使用本记录 Verification 中的只运行已有依赖命令。
2. 独立复核、最终树验证与授权齐备后，controller 提交并按项目 PR/squash 约定集成。
   **main 推送会触发网站生产部署**，因为版本与站点文件在 `site.yml` 的触发范围内；不能把它当作只存代码。
   确认 GitHub 活动身份（`gh auth status`）、目标仓和部署环境，记录提交、PR 与工作流链接。
3. 如需四平台预演，经授权执行 `gh workflow run release.yml --ref main -f ref=<最终已推送的提交或分支>`。
   `workflow_dispatch` 仅构建与校验，不创建 Release，也不更新 Homebrew。等待四目标构建与归档校验全部通过。
4. 获得明确发版授权后，由 controller 在核对过的发布 commit 上创建并推送 `v0.3.4` tag。
   tag 必须与 `Cargo.toml` 一致；release 流水线构建 macOS arm64/x86_64 与 Linux musl arm64/x86_64，
   打包 App、许可证与 SHA256 校验文件，检查归档后才创建 GitHub Release。
5. 发布后核验 Release 的 tag/commit、四份归档与校验文件、macOS App 签名及版本、Homebrew 公式。
   `TAP_DEPLOY_KEY` 缺失时流水线会跳过自动更新公式，需要另行授权补齐；不能把 skip 记作成功。
   流水线凭据来自 GitHub Secrets（`TAP_DEPLOY_KEY`、`CLOUDFLARE_API_TOKEN`、`CLOUDFLARE_ACCOUNT_ID`），不落盘。
6. 网站部署后检查中英文首页、更新记录和 Markdown/MCP，以及新版本下载链接实际可用。
   用户设备安装或升级另行授权；检查 CLI/App/后台入口版本一致，不以重开用户会话作为冒烟步骤。
   最后补录真实执行结果、发布 commit/tag、run 和 Release 链接，将本记录从 prepared 改为已发布。

## Rollback procedure

**尚未部署，无本次发布需要回滚。以下是执行发布前须落实的回滚准备。**

1. 安装前保留上一正式版 v0.3.3 的 CLI、App、入口位置和后台配置，记录校验值；运行中数据库用 SQLite backup
   保存一致快照，不直接复制正在写入的数据库文件。备份只放私有位置，不进入此公开仓。
2. 本机升级失败时先退出 App、停止 cc-moss 后台（不结束普通用户会话），按备份 manifest 恢复 CLI/App 和后台入口。
   macOS 二进制先复制到同目录临时名再原子 `mv`，不要原地覆盖；按已核对的旧版配置重新启动并用
   `cc-moss --version`、`cc-moss doctor`、App 关于页确认同为 0.3.3。
3. 没有本地包备份时，从 `https://github.com/larrykoo711/cc-moss/releases/tag/v0.3.3` 获取对应平台包与
   SHA256SUMS，在独立空目录校验后按既有安装路径恢复。`cc-moss update` 追随最新版，不是降级命令。
4. 仅回退二进制不承诺撤销新版写入的运行状态。不要自动覆盖登记表；需要恢复快照时必须先另行确认，
   并说明会丢失备份之后的会话登记变化。历史 orphan 或错配记录不在自动回滚范围内。
5. 公开发布出现问题时不移动已发布 tag；经授权修正发布说明、Homebrew 公式或追加修复版本。
   网站通过回退相关提交并走原站点流水线恢复；这仍是生产部署，必须另行授权。
