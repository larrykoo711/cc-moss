# T2.1 设计笔记：`cc-moss daemon`

> 一页纸。合同在 `tasks/*/T2.1-daemon.spec.md`；这里只写怎么做、为什么这样做。

## 模块划分

| 位置 | 内容 | 依赖 |
|------|------|------|
| `moss-core/src/daemon/mod.rs` | `LABEL`、`Paths`（`<state>/daemon/` 下的各文件）、日志追加与轮转、心跳间隔常量 | — |
| `moss-core/src/daemon/lock.rs` | 单实例锁：`std::fs::File::try_lock`（Unix 上就是 `flock(LOCK_EX\|LOCK_NB)`） | std |
| `moss-core/src/daemon/status.rs` | `status.json` 的读写（临时文件 + rename）与 `Report`（`status --json` 的契约） | `proc::Liveness` |
| `moss-core/src/daemon/ladder.rs` | 通用看护部件：`RestartLadder` + `Watchdog`，纯逻辑，时钟由调用方传入 | — |
| `moss-core/src/daemon/plist.rs` | LaunchAgent plist 生成（XML 转义） | — |
| `cc-moss/src/cmd/daemon.rs` | `run / start / stop / status`；`Launchctl` 接口（真实 + 记录用的假实现）；install / uninstall / doctor 调用的入口 | moss-core |

moss-core 只放「不碰系统」的部分，全部能单测；跟 launchctl、信号、进程打交道的放 cc-moss。

## 锁与状态文件

- `daemon run` 先拒绝 root（`app::as_root()`，与 start / stop 同一句话）：sudo 留下的 root 属主锁、状态、日志会让用户自己的守护进程永远 EACCES。
- `<state>/daemon/lock`：`daemon run` 一开始就 `try_lock`。拿不到 → 打印「已经有一个在跑（pid N）」退出码 1，**不碰 status.json**。若是 launchd 拉起的那份（`XPC_SERVICE_NAME` = label），不往 stderr 打印（只写 daemon.log，并截断过大的 stdout/stderr.log），先睡 5 分钟再退出：否则用户在终端前台跑着一份时，launchd 每 30 秒重拉一次、stderr.log 越写越大。进程死（含 `kill -9`）内核即释放锁，不会留死锁。std 打开文件带 `O_CLOEXEC`，以后 T2.2 拉起的子进程不会继承锁。
- `<state>/daemon/status.json`（0600，原子写）：`{schema:1, pid, pid_start, version, started_ms, heartbeat_ms}`。只在拿到锁之后写；心跳每 30 秒刷新（测试里用 debug 版环境变量缩短）。
- 判断「在不在跑」（`status`、doctor、install、App）：以 status.json 里的 pid 为准，用 `proc::liveness(pid, pid_start)` 比对进程启动时间，防 pid 复用。`Dead` → 没在运行（陈旧状态）；`Alive` 且记录了启动时间 → 运行中。分不清是不是复用的 pid 时（`Unknown`，或 `pid_start` 为空——`ps` 超时没读到，此时任何占着该 pid 的进程都会比成 `Alive`）由心跳决定：3 个周期（90 秒）内有心跳算运行中，更旧算没在运行。守护进程启动时读自己的启动时间最多试 3 次。（评审 M4：原先 `Unknown` 一律当运行中，复用 pid 会让 start 跳过 kickstart。）
- 状态目录以 LaunchAgent 钉住的为准：`status` / doctor / App / `start` 先读已安装 plist 里的 `EnvironmentVariables.CC_MOSS_STATE_DIR`，没有 plist 才用当前环境。`daemon start` 发现 plist 钉的目录和当前环境不同，不重写 plist、不 bootout，只说明并提示在新环境里跑 `cc-moss install` 来迁移；install 迁移时说一句「文件现在放在 X（之前在 Y）」。（评审 I1：从 Dock 启动的 App 没有用户 shell 里的变量，否则会看错目录、点「启动」把守护进程来回挪。）`status` **不去试锁**：试锁的那一瞬间正好撞上新起的守护进程，会把它挤走。
- 收到 SIGTERM / SIGINT（`signal-hook` 置位一个原子布尔，已在依赖树里）：写一行日志，删掉 status.json（只删 pid 是自己的那份），退出 0。

## 日志

- `<state>/daemon/daemon.log`：守护进程自己写，每行一次 `write`，超过 1 MiB 删掉重开（与 `hook.log` 同策略）。
- launchd 的标准输出 / 错误进 `<state>/daemon/stdout.log`、`stderr.log`。launchd 拿着这两个文件的 fd，不能删；守护进程启动时若超过 1 MiB 就截断为 0（`O_APPEND` 下截断安全）。

## 重启阶梯（给 T2.2 用）

- `RestartLadder`：失败次数 n → 等待 `[30s, 2m, 10m, 1h][min(n,3)]`；上一次启动后稳定运行 ≥ 10 分钟再失败，从 30s 重新开始。
- `Watchdog::check(now, liveness)`：`Up` 时 `Alive | Unknown` → 继续；`Dead` → 按阶梯算出 `retry_at`；`Down` 时到点 → `StartNow`。调用方启动后调 `started(now)`。`now` 是参数，测试里用 `Instant` + 偏移，不睡觉。
- 本任务不接子进程；守护进程主循环只做锁、心跳、日志、信号。

## LaunchAgent plist

`~/Library/LaunchAgents/io.github.larrykoo711.cc-moss.daemon.plist`：

- `Label`、`ProgramArguments = [<稳定的 cc-moss 路径>, "daemon", "run"]`（与 hook 同一取法：PATH 上指向本二进制的稳定入口，如 Homebrew 的 `bin` 链接）
- `RunAtLoad true`、`KeepAlive true`、`ThrottleInterval 30`、`ProcessType Background`
- `StandardOutPath` / `StandardErrorPath` → `<state>/daemon/{stdout,stderr}.log`
- `EnvironmentVariables.CC_MOSS_STATE_DIR = <install 时的状态目录>`：launchd 不给用户 shell 的环境，钉死目录才能让 CLI、App 与守护进程看同一份状态
- 所有字符串做 XML 转义（路径含空格、`&` 也正确）

## install / uninstall / 升级 / start / stop 的 launchctl 步骤

域 `gui/<uid>`，服务 `gui/<uid>/<label>`。只在 macOS 上做。

| 场景 | 步骤 |
|------|------|
| install，没加载 | 写 plist → `bootstrap gui/<uid> <plist>` |
| install，plist 内容变了（换了路径） | 写 plist → `bootout gui/<uid>/<label>` → `bootstrap` |
| install，plist 没变但在跑的版本 ≠ 当前版本（升级） | `kickstart -k gui/<uid>/<label>` 换上新二进制 |
| install，用户之前 `daemon stop` 过（disabled） | 只写 plist，不拉起，提示 `cc-moss daemon start` |
| uninstall | `bootout`（没加载就忽略；失败只提示，继续）→ 被停用过就 `enable`（launchd 的停用标记不随 plist 删除，否则重装后仍「保持停止」）→ 删 plist；sudo 下不动，提示去掉 sudo |
| `cc-moss update` 成功后 | plist 在、已加载、没被停用 → `kickstart -k` 换上新二进制；失败只提示 |
| `daemon start` | 写 / 更新 plist（钉的状态目录不同则保留原 plist）→ `enable` → 没加载就 `bootstrap`，加载了就 `kickstart` → 等 status 变成运行中（最多几秒）；kickstart 报错（launchd 可能正在拉起它）也先等，等不到才报那个错 |
| `daemon stop` | `disable`（下次登录也不起）→ `bootout` → 等 status 变成没在运行 |

「已加载」= `launchctl print gui/<uid>/<label>` 成功；「被停用」= `launchctl print-disabled gui/<uid>` 里该 label 为 disabled。

### 测试开关（不碰真实 LaunchAgents 与 launchctl）

- `CC_MOSS_LAUNCHD_DIR`（仅 debug 构建生效，同 `app.rs` 的 `test_override`）：plist 写到这个目录，launchctl 换成**记录用的假实现**——每次调用追加一行到 `<dir>/launchctl.log`，不执行；「已加载 / 已停用」从这份记录推出来（最后一次 bootstrap 晚于 bootout 即已加载）。
- 没有这个开关时，若 `HOME` 不是本账户真实的家目录（`getpwuid_r(getuid())` 的 `pw_dir`，经 libc，网络账户同样适用；比较时解符号链接、忽略末尾斜杠，测试都用临时 HOME），只写 plist、不调 launchctl，并在 install / uninstall 输出里说明 launchd 没参与：launchd 只读真实家目录下的 LaunchAgents，向它注册临时目录里的 plist 毫无意义，还会污染用户的 launchd。双保险，现有的 `install_cli` 用例（临时 HOME + `CC_MOSS_PLATFORM=macos`）因此不会碰到真实 launchd。
- 第三道保险（评审 I4）：debug 构建里只要设了 `CC_MOSS_FORBID_LAUNCHCTL`，构造真实 launchctl 或执行任何 `/bin/launchctl` 调用都直接 panic。`tests/common::bin()`（以及自己清环境的 `aliases_cli`、tmux 里跑的 `pick_e2e`）对每个测试都设上它；把 `is_own_home` 改成恒 true，`install_cli` 会成片变红而不是悄悄动开发者的 launchd。
- 记录用的假实现还认 `CC_MOSS_LAUNCHCTL_FAIL=bootout,…`（debug），让指定调用失败，用来测 install / uninstall 出错时继续往下走。所有测试开关都经 `app::test_override`（只在 debug 构建生效）。
- install 的守护进程这一步连准备都失败（`HOME` 未设、状态目录不是绝对路径、程序路径不是 UTF-8）也只提示，不中断后面的 install。
- 通用看护部件加了 `Watchdog::start_failed(now)`：拉不起来的子进程也按阶梯等，不会一直 `StartNow` 空转。

## App 读状态的方式

- `MossKit/DaemonStatus.swift`：解码 `cc-moss daemon status --json`（`schema ≤ 1`），`MossClient.daemonStatus()` / `startDaemon()`（跑 `daemon start`）。
- `CCMoss/MossSettings.swift`：设置新页「Moss」，一张卡一行：「守护进程 · 运行中 3 小时」或「没在运行」+「启动」按钮；页面在前台时每 5 秒重读一次。
- 三种状态（`MossKit.DaemonCheck`）：正在查看 / 有结果（运行中、没在运行）/ 查不到（cc-moss 报错、超时、App 找不到 cc-moss），查不到时显示原因，不再冒充「没在运行」，也不会一直停在「正在查看…」。
- 离屏渲染：`--settings moss --daemon running|stopped|unknown` 用固定的状态画图，不跑 cc-moss。
