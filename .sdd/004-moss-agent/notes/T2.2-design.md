# T2.2 设计笔记：Moss 常驻

> 一页纸。合同在 `tasks/*/T2.2-moss-resident.spec.md`；这里只写怎么做、为什么这样做。

## 模块划分

| 位置 | 内容 | 碰系统吗 |
|------|------|---------|
| `moss-core/src/moss/mod.rs` | 常量（socket `cc-moss-moss`、会话名 `moss`、角色 `moss`、环境变量 `CC_MOSS_ROLE`）、`home_dir(state)`、`status.json` 读写（`<state>/daemon/moss.json`） | 读写文件 |
| `moss-core/src/moss/home.rs` | 家目录布置：给定一组 `(相对路径, 内容, 种类)` 写进家目录；受管覆盖、用户文件只建不改、补齐 `journal/` `memory/`；卸载只删受管文件；`SESSIONS.md` 生成 | 文件 |
| `moss-core/src/moss/guard.rs` | 防护 hook 的判定纯函数 `decide(home, cwd, tool, input) -> Decision` | 只读 `canonicalize` |
| `moss-core/src/moss/keeper.rs` | 看护状态机 `Keeper`：输入（开关、判活结果、现在几点），输出（启动 / 结束 / 等）；判活分类 `classify_has_session` | 不碰 |
| `cc-moss/templates/moss/**` | 模板原文，`include_str!` 打包进二进制 | — |
| `cc-moss/src/cmd/moss.rs` | `moss start\|stop\|status [--json]`、`moss profile`、`hook moss-guard` 入口、install / uninstall / doctor 步骤、守护进程里的看护循环（真 tmux） | 是 |

纯逻辑（布置规则、判定、状态机）全在 moss-core 里单测；跟 tmux、进程、registry 打交道的在 cc-moss。

## 家目录 `<state>/moss/`

默认 `~/.local/state/cc-moss/moss/`，不在 `~/Documents` 这类受隐私保护的目录下（K7：launchd 拉起的进程读受保护目录会卡在授权上）。

| 文件 | 种类 | 规则 |
|------|------|------|
| `CLAUDE.md` | 受管 | 每次布置覆盖。`@SECURITY.md` `@IDENTITY.md` `@SOUL.md` `@USER.md` 依次引入，再写几条做事规矩；`SESSIONS.md` 不引入（I8：别的会话的名字和备注不能成为指令级上下文），写明按需当资料读 |
| `SECURITY.md` | 受管 | 最高优先级：只写自己的家、不碰 token、不泄露路径、破坏性动作先问 |
| `.claude/settings.json` | 受管 | 防护 hook 与 Bash 沙箱（见下）；cc-moss 的绝对路径与家的路径都在 hook 命令里（shell 单引号转义） |
| `.claude/skills/moss-profile/SKILL.md` | 受管 | 改人设的唯一入口：说明用 `cc-moss moss profile <identity\|soul\|user>` 从标准输入写入 |
| `IDENTITY.md` `SOUL.md` `USER.md` | 用户 | 不存在才建，之后绝不覆盖（包括内容为空、被改过、是符号链接） |
| `journal/` `memory/` | 用户 | 不存在才建目录（`journal/README.md` 一句话说明格式） |
| `SESSIONS.md` | 生成 | 守护进程按 registry 写会话一览；每 60 秒或 registry 的事件序号变化时重写，内容没变不写 |

- 布置时机：`cc-moss install`（macOS）以及守护进程每次拉起 Moss 之前。后者让 `brew upgrade` 之后不跑 install 也能拿到新的受管文件，且 hook 里的 cc-moss 路径始终是当前这个。
- 写法：先写临时文件再 rename（受管）；用户文件用 `create_new`，已存在（含悬空符号链接）就跳过，绝不截断。
- **不跟随链接（I2）**：家本身和每一级目录都 `lstat`；是链接或类型不对就删掉链接本身、建真目录；临时文件先删同名残留再 `O_EXCL | O_NOFOLLOW` 打开，rename 替换目标处的链接而不是写穿；布置时清掉 `.claude/` 下所有非受管的东西；卸载整个删 `.claude/`（链接只删链接），父目录是链接的文件跳过。`SESSIONS.md`、`moss profile` 的快照与人设文件都走同一条路。
- 卸载（`install --uninstall`）：删受管文件，留下 IDENTITY / SOUL / USER / journal / memory；家目录里只剩空目录时一并删掉。
- `moss profile <name>`：先把旧内容复制到 `.snapshots/<NAME>-<时间>.md`，再原子写入新内容。这是给 `/moss-profile` skill 用的门。

## 防护 hook（fail-closed）

项目级 `.claude/settings.json`：

```json
{"hooks":{"PreToolUse":[{"matcher":"*",
  "hooks":[{"type":"command","command":"'<cc-moss>' hook moss-guard --home '<home>' || exit 2"}]}]},
 "sandbox":{"enabled":true,"failIfUnavailable":true,"allowUnsandboxedCommands":false,
  "autoAllowBashIfSandboxed":true,"excludedCommands":["cc-moss moss profile *"],
  "filesystem":{"allowWrite":["<state>/registry.db","…-wal","…-shm","…-journal"],
                "denyWrite":["./SECURITY.md","./CLAUDE.md","./SESSIONS.md","./IDENTITY.md","./SOUL.md","./USER.md"]}}}
```

- **评审修正轮（I1/I9）**：matcher 改 `*`；`decide()` 对不认识的工具（含 `mcp__*`、`EnterWorktree`、`PowerShell`）拒绝，只放行已知只读 / 只动会话自身状态的工具（`HARMLESS` 表）和家内的文件写；`Bash` / `Monitor` 交给沙箱，文字检查只为给出原因（按词匹配、跳过 heredoc 正文，M2）。家从 hook 命令行的 `--home` 取，不读 `CLAUDE_PROJECT_DIR`，缺了就拒绝。
- **沙箱的取舍**（文档：code.claude.com/docs/en/sandboxing、settings-reference）：默认可写 = 工作目录（家）+ 每用户临时目录；`allowWrite` 只加 registry 四个文件（`cc-moss ls` 等命令要写 WAL）。没有放 tmux socket 目录：macOS 沙箱默认拦所有 Unix socket，放开 Moss 的或用户的 tmux socket 等于给沙箱开后门（tmux 里起的命令在沙箱外跑），所以沙箱里的 Moss 连不上任何 tmux——T3.1 的「手」要走别的路（经守护进程）。`denyWrite` 让人设与受管文件对命令行只读；改人设的唯一出口是 `excludedCommands` 里的 `cc-moss moss profile *`（实测：heredoc 与 `<` 重定向形式都留在沙箱里，`--from <草稿>` 形式才出沙箱，所以 skill 改用 `--from`；与别的命令串在一起时整条留在沙箱里）。
- 真机探针（Claude Code 2.1.302，临时状态目录，见 REPORT）：Bash 往家外写 `Operation not permitted`、`dangerouslyDisableSandbox` 无效、python 写家外被拒、`touch ~/x` 被拒、家内写可以、`cc-moss ls` 能跑、`echo x > SOU?.md` 被沙箱拒、Write 工具写家外被防护拒、家内可写、`.claude/` 被拒；`tmux -L 新 socket` 起不来。注意：探针目录若在 Claude Code 自己的临时目录（`/tmp/claude-<uid>`）下，那里本来就可写，会造成假阳性。

- `cc-moss hook moss-guard` 在 `main.rs` 里先于普通 hook 分流（不进 `hook.rs` 的代答 / 登记逻辑）。放行 → 退出 0、不输出；拒绝 → 原因写 stderr、退出 2（Claude Code 对 PreToolUse 退出 2 的约定是拦下并把 stderr 给模型）。
- **出错一律拒绝**：读不了 stdin、JSON 不对、缺 `file_path`、panic，都走拒绝。命令后面的 `|| exit 2` 兜住 cc-moss 根本跑不起来的情况（找不到程序 127、崩溃 101），不会因为非 2 的退出码被当成「hook 出错、照常放行」。这和代答 hook 相反：代答 hook 出错要让会话照常走，防护 hook 出错要让 Moss 停手。
- 判定 `decide(home, cwd, tool, input)`：
  - `Write` / `Edit` / `MultiEdit` 取 `file_path`，`NotebookEdit` 取 `notebook_path`；相对路径按 payload 的 `cwd` 解析。
  - 规范化：先按字面消掉 `.` 和 `..`，再把「最长的已存在前缀」`canonicalize`（解开符号链接）后接上剩下的部分；家目录本身也 `canonicalize`。这样 `home/link -> /etc` 下的写入、`home/../x`、指向家外的符号链接文件都能识破。
  - 家外 → 拒绝。家内的 `.claude/` 下所有文件（settings、hooks、受管 skill）、`SECURITY.md`、`CLAUDE.md`、`SESSIONS.md` → 拒绝（自身配置与受管文件）。`IDENTITY.md` / `SOUL.md` / `USER.md` → 拒绝，原因里指向 `/moss-profile`。其余家内文件放行（journal、memory、自己的笔记）。
  - `Bash`：命令文本只做尽力而为的一层——提到受保护文件（`.claude/settings`、`.claude/hooks`、`SECURITY.md`、`CLAUDE.md`、人设三件）且带写入迹象（`>`、`tee`、`sed -i`、`mv`、`cp`、`rm`、`ln`、`truncate`、`chmod`、`perl -i`）→ 拒绝；`cc-moss moss profile` 放行。Bash 是 Moss 的手（T3.1 起它要跑 cc-moss 命令），没法靠解析命令行管住家外写入；这一点写进 SECURITY.md 当规矩，真正的手（派发、关闭）到 T3.1 都经 cc-moss 命令与审计。
  - 其它工具 → 修正轮起：已知无害的放行，其余拒绝。

## 看护循环与 Watchdog 的接法

守护进程主循环原来每 100ms 醒一次只管心跳；现在每次醒来再调一次 `MossKeeper::tick(now)`（cc-moss 里，持有真 tmux），它内部按节拍做事：

1. **开关**：每秒读一次 `[moss] enabled`（`config.toml`，缺省 true）。关 → 若在跑就 `kill-session`、关掉 Moss 的 registry 记录、清掉 `moss.json`，状态机回到「关」；开 → 状态机回到「未启动」。
2. **判活**：每 60 秒（测试里缩短）跑 `tmux -L cc-moss-moss -f /dev/null list-panes -a -F '#{session_id}|#{@cc-moss-role}|#{pane_dead}'`，`classify_panes`：有 `@cc-moss-role=moss` 且 pane 未死 → `Alive`；有标记但 pane 全死（`remain-on-exit`，I3）→ `Dead`，顺手 `kill-session` 清掉；失败时按 `classify_has_session(stderr)`：
   - 退出 0 → `Alive`
   - 非 0 且 stderr 含 `can't find session` / `no server running` / `error connecting to`（socket 文件不在）→ `Dead`
   - 其它一切（超时、tmux 不在 PATH、别的报错）→ `Unknown`，`Watchdog` 当活着处理（宁漏不误杀）
3. **Watchdog**（`daemon/ladder.rs`，原样复用）：`check(now, liveness)` 返回 `Running` / `WaitUntil` / `StartNow`。
4. **启动**（`StartNow`）：先再判一次活（以防它自己回来了）→ 布置家目录 → 新 uuid → `tmux -L cc-moss-moss -f /dev/null new-session -d -s moss -c <home> -e CC_MOSS_ROLE=moss -e CC_MOSS_MOSS_SESSION=<uuid> <claude> --dangerously-skip-permissions --session-id <uuid> <开机提示> ; set-option @cc-moss-role moss ; set-option destroy-unattached off ; set-option -w remain-on-exit off` → 等 500ms 看是否立刻退出。成功 → `Watchdog::started`，写 `moss.json`，清掉 `moss-error.txt`，**这时才**关旧记录（I7：`close_role(moss, socket, keep=新 uuid)`）；`new-session` 报 `duplicate session` → 补上标记、当作接管，不关任何记录；其它失败 → `Watchdog::start_failed`，写 `moss-error.txt`（`status --json` 的 `last_error`），按阶梯等。
   开关（M1）：守护进程起来后先读到一次 config 才动作，读不了就什么都不做。关着时（I4）每次判活看到 `Alive` 都再停一次；`end_moss` 在 `Unknown` 时也尝试 `kill-session`，事后判活不是 `Dead` 就报错，不关记录、不删 `moss.json`；`moss stop` 照实报错（开关已关）。
5. **接管**：守护进程启动（含升级后 `kickstart -k`）时先判一次活，`Alive` 就直接 `started`，沿用 `moss.json` 里的 since / restarts / session_id，不重开一个。
6. **重启计数**：一次死亡后的成功重启 +1；从「关」或守护进程冷启动且没有可接管的会话时归零。
7. 每次都全新启动、不 resume：身份和进度都在文件里，崩溃前的 TUI 状态不可信（reference-study §2.5）。

纯状态机 `moss_core::moss::keeper::Keeper` 只吃 `(now, enabled, liveness)`，吐 `Action::{Nothing, Start, Stop}`，内部包一个 `Watchdog`；单测用注入的 `Instant` 覆盖在场 / 明确死亡 / 未知错误 / 起不来四种输入。cc-moss 那层只负责把 Action 变成 tmux 调用并把结果喂回去（`started` / `start_failed`）。

### 测试开关（`app::test_override`，只在 debug 生效）

- `CC_MOSS_MOSS_SOCKET`：tmux socket 名。**测试里没设它时（`CC_MOSS_FORBID_LAUNCHCTL` 在场），守护进程不碰 Moss**：现有 `daemon_e2e` 不会意外连到真实的 `cc-moss-moss`。修正轮（M6）：只要 `CC_MOSS_FORBID_LAUNCHCTL` 在场就返回 `None`（release 构建读不到覆盖值，也就碰不到真 Moss）；依赖这些开关的测试调 `common::debug_only()`，release 下直接拒跑。
- `CC_MOSS_MOSS_CHECK_MS`（判活间隔）、`CC_MOSS_MOSS_STEPS_MS`（逗号分隔的阶梯，替换 30s/2m/10m/1h）。阶梯注入走 `Watchdog::with_steps`（新增构造，默认仍是 `STEPS`）。
- e2e 的 socket 名带 `cc-moss-test-<pid>-` 前缀，测试结束 `kill-server` 并删 socket 文件。

## 专用 tmux socket

- `tmux -L cc-moss-moss`，会话名 `moss`。不和用户的 tmux server 混：用户 `tmux kill-server` 不会带走 Moss，Moss 的 server 由守护进程（launchd）第一次 `new-session` 时拉起，继承守护进程的环境与隐私授权（K7）。
- hook 的改名同步（`sync_tmux_name`）对 Moss 跳过（修正轮起按 registry 里的 role 判断，不再看环境变量）。判活认 `@cc-moss-role` 标记而不是名字（M7），手动改名也不会误判死亡。
- 不读用户的 tmux.conf（`-f /dev/null`，M10/I3）：插件、`remain-on-exit`、`destroy-unattached` 都影响不到 Moss 的死活。

## role 的登记链路

`CC_MOSS_ROLE=moss` + `CC_MOSS_MOSS_SESSION=<uuid>`（`new-session -e`）→ claude 进程环境 → hook 子进程继承 → `hook.rs` 在 SessionStart 落库后，**只有 `session_id` 等于 `CC_MOSS_MOSS_SESSION` 时**调用 `registry.set_role(slot, "moss")`（I6：在 Moss 的 tmux 里新开窗口、Moss 的 shell 起的 tmux server、别处 `--resume` Moss 的 id，都继承了 `CC_MOSS_ROLE` 却不是 Moss）；`close_role` 也只关 Moss socket 上的记录 → registry 新列 `role TEXT`（`ensure_columns` 原地补列，schema 不变）→ `Slot.role` → `ls --json` 加 `"role": "moss"`（其它会话为 `null`，加字段不改 schema）。

用到 role 的地方：
- `close` 拒绝 Moss（提示到设置里关）；`pick` 的 Moss 行菜单没有「结束会话」，`end()` 也再拦一次；中断的 Moss 记录不进 pick 的「断了的」列表，也不进 `restore` 计划（守护进程会自己把它拉回来，恢复它只会多出一个）。
- App：`Session.role`；面板顶部固定一行 Moss（只取在跑的那条），不进按目录分组，也不进「找回」；RowActions 对 Moss 没有「不再提醒」。

## `moss status --json`

`{"schema":1,"enabled":bool,"running":bool,"since":rfc3339?,"restarts":int,"session_id":str?,"daemon_running":bool,"last_error":str?}`

- daemon_running / last_error（M3）：App 据此显示「在等守护进程」「没能启动（原因）」，不再一直「正在启动…」。
- enabled（读守护进程 plist 钉住的 `CC_MOSS_CONFIG`，I5）：`[moss] enabled`；running：tmux 判活 `Alive`（`Unknown` 时退回看 `moss.json` + 守护进程在不在跑）；since / restarts / session_id：守护进程写的 `<state>/daemon/moss.json`。放在 `daemon/` 而不是 Moss 的家里：Moss 能写自己的家，不该能改自己的状态。
- `moss stop`：`config set moss.enabled false`（沿用 `config set` 的原地编辑），再直接结束 tmux 会话、关掉记录（守护进程没在跑也能停下）；守护进程下一秒读到关，也不会再拉。`moss start`：设回 true；守护进程没在跑就提示 `cc-moss daemon start`。`moss.enabled` 加进 `config get|set` 的键表。

## plist

- `ProcessType` 由 `Background` 改 `Standard`（M13：Background 会把 Moss 和它起的进程压成低优先级 I/O 与 CPU）。
- `EnvironmentVariables` 加 `CC_MOSS_CONFIG`（I5）与 `PATH`：修正轮（M5）起每次 install 按当前 PATH 重建（离开 PATH 的旧目录不再留着），文件夹集合与已装 plist 相同时原样保留（顺序稳定）；当前 PATH 之后补 `/opt/homebrew/bin`、`/usr/local/bin`、`~/.local/bin`、`~/.claude/local`、`/usr/bin`、`/bin`、`/usr/sbin`、`/sbin`，去重、去空。
- doctor：Moss 开着时，只按 plist 里的 PATH 找 `claude` 与 `tmux`（不再算当前终端的 `CC_MOSS_CLAUDE_BIN`，守护进程没有它），找不到就给修复提示（装上它 / 重新 `cc-moss install` 让 PATH 补上）。纯函数 `moss_check(facts)` 单测。

## App 页面

- MossKit：`Session.role` / `isMoss`（没名字时标题是「Moss」）；`Grouping.splitMoss(_:)` 在快照入口把 Moss 拆出来（在跑的那条做固定行，其余 Moss 记录哪里都不出现），于是分组、计数、菜单栏图标、「找回」、启动提醒天然不含 Moss；`Grouping.projects` 与 `Close.allowed` 再各挡一次；`RowActions` 对 Moss 主动作固定为打开、不给 `.close` / `.stopReminding` / `.bringBack` / `.rename`；`Filter.keeps` 让固定行跟着搜索与状态筛选；`MossStatus`（解 `moss status --json`，`line()` 出「Moss · 运行中 2 小时（重启过 1 次）」/「Moss · 已关闭」）；`MossClient.mossStatus()` / `setMoss(_:)`。
- 设置 › Moss：在原「后台」卡片上方加「Moss」卡片：状态行 + 开关（调 `moss start|stop`）。离屏渲染 `--settings moss --moss running|stopped`。
- 面板：会话列表最上面固定一行 Moss（`SectionHeader` 风格的小标题「Moss」+ 行），过滤时只要它匹配就留着。
- 修正轮（M4）：Moss 不算会话数，但它「需要你」时进菜单栏图标与数字（`Grouping.alerting`）；提醒按 id 找会话时也认 Moss（`AppModel.session(_:)`）。
- 卸载顺序（M8）：先 bootout 守护进程，再停 Moss、删受管文件。`daemon stop` 也结束 Moss（R-a，`end_reason = daemon-stopped`）。
