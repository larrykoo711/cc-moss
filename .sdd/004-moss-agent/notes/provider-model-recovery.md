# F42：切换渠道后恢复会话的模型选择（2026-10-21）

状态：调研与方案草案；未实施，未通过真实请求验收。

## 用户证据与安全只读观察

- 用户报告切换渠道并重开后，旧会话请求旧模型，返回 `400 unknown provider for model ...`；手动 `/model` 选择新渠道模型后才继续。
- Claude Code 版本：2.1.306；cc-moss：0.3.3。
- 当前渠道配置的 `ANTHROPIC_MODEL` 与 `ANTHROPIC_DEFAULT_*_MODEL` 指向不同模型；不能把别名映射当作固定默认模型。
- cc-moss 能看到新供应商地址；采样时 5 个运行会话的 `provider_restart` 为 `model`。这是配置差异标记，不是实际请求路由证明，也不能据此断言用户没有重开。
- 只读取模型字段、环境变量键名与必要状态；未输出凭据，未修改供应商配置，未重启真实会话。

## 目标与建议边界

1. 读取会话实际使用的配置来源，不直接依赖渠道管理器的私有数据库，也不假定全局 settings 是唯一来源。
2. 区分两种意图：普通重开保留模型；应用当前渠道配置则恢复同一会话并显式选择当前渠道默认模型。
3. 对渠道应用操作显示目标模型及来源。固定模型与别名映射冲突时不偷偷改配置，也不凭模型名字猜哪个有效。
4. 不在 400 后盲试多个模型，不自动重放用户上一条消息，不中断活跃任务；忙碌会话沿用完成后排队机制。
5. 手动重开入口不依赖自动识别标记；非 tmux 会话先走已有接管引导。
6. 配置变化提示、重开进程成功、首个请求实际采用目标模型是三个不同状态，不混为“切换成功”。

## 隔离验收矩阵（拟）

- 渠道 A 的旧模型恢复到渠道 B 的固定默认模型：会话 ID 和历史不变，请求 model 为 B 的配置值。
- 旧启动参数带 `--model`：渠道应用只保留一个明确目标；普通重开仍保留原选择。
- 固定模型和别名映射不同：固定模型来源可见，不能静默改用别名目标。
- 仅新增 endpoint / key / alias、没有固定模型：也要有手动应用渠道配置的路径，不保证热切兼容。
- 项目覆盖与独立配置目录：采用该会话生效来源，而不是另一份全局配置。
- 渠道默认模型本身无效：报清晰错误并引导修改渠道配置或手选模型，不无限重试。
- busy 排队、排队后再换渠道、切回订阅、非 tmux、普通手动重开均有独立用例。

## 已核实的代码锚点

- `crates/cc-moss/src/cmd/restart.rs:84–105`：有固定模型时仅移除旧 `--model`，未显式追加当前渠道模型；不能据此保证恢复会话请求模型已改变。
- `crates/cc-moss/src/cmd/restore.rs:426–436`：普通恢复直接回放白名单中的旧模型参数。
- `crates/moss-core/src/provider.rs:293–307`：判定依据为键删除、固定模型变化；端点变化或仅新增别名不会直接标记需要重开。配置可热读不等于旧会话模型与新端点兼容。
- `crates/cc-moss/src/cmd/provider.rs:75–96`：排队项目前仅持有 slot、recheck、attempts；若增加模型策略，必须一并持久化，否则延后执行会丢失操作意图。
- `apps/macos/Sources/MossKit/Provider.swift:130–154`：当前行内重开入口受 providerRestart 标记限制。
- `crates/cc-moss/src/cmd/moss.rs:1376–1394,1670–1686`：Moss 是新会话路径，不应与普通 resume 会话混同；模型解析可以共享，生命周期语义不强行合并。

最小实现建议：统一模型选择策略与 argv builder，让 restart、restore 的“应用渠道默认模型”显式附加目标模型；保留普通重开语义。排队持久化策略，并在执行时重新检查配置。新默认模型的优先级和无固定模型的回退仍待 CLI 层验证。

## CLI 文档核对（非请求级实测）

官方模型文档说明恢复会话会保留 transcript 中保存的模型，但新启动的 `--model` 或 `ANTHROPIC_MODEL` 可覆盖恢复模型。因此，本次即使已重开仍请求旧模型，也不能只归因于 transcript：还需核对该次启动实际读到的设置来源、环境以及 hook 时序。

- 显式渠道应用候选命令：`claude --resume <id> --model <target>`；不带 `--fork-session`，保留原会话 ID。
- 固定模型优先于顶层模型及别名选择；family 映射负责解析别名，不等于统一默认值。
- 无明确模型时，文档支持 `default` 清除模型 override、使用账户运行时默认；`--resume ... --model default` 仍须在 2.1.306 完成请求级隔离实测后才能作为已验证分支。
- 当前重开命令提交成功不等于新 SessionStart 完成，更不等于请求目标模型成功。

参考：https://code.claude.com/docs/en/model-config#setting-your-model 、https://code.claude.com/docs/en/cli-reference#cli-flags 、https://code.claude.com/docs/en/settings#settings-precedence 、https://code.claude.com/docs/en/env-vars#precedence 。

## F43：重开提示与操作的 UX 草案（待用户批准）

证据：用户截图显示标题旁只有很小的黄色刷新图标；已手选模型的会话仍显示标记，用户无法区分状态是否过期。不能只放大图标而继续把配置差异当作实际故障。

- 列表摘要用文字状态替代孤立小图标：已知待应用显示「待应用渠道」；只有配置差异但不知实际模型显示「模型待确认」。不依靠颜色区分，不覆盖原有会话运行状态。
- 状态入口展开行内说明区：展示目标模型与来源（渠道默认 / 手动选择），主按钮「应用并重开」；busy 改「本轮结束后应用」，排队后可取消。
- 行内说明区承担唯一主操作；不在标题和右侧工具栏重复两个含义不明的 refresh。普通「重开会话」放通用菜单，与应用渠道配置区分。
- 用户已手动选择模型：有可信运行证据时重新计算状态；缺少证据时允许「保留当前选择」并仅确认本次配置变更，不宣称验证 API 成功。下一次相关配置变化重新提示。
- 执行反馈分为等待本轮结束、正在重开、会话已恢复、需要处理；恢复确认依赖新会话启动事件，不以已发送启动命令作为成功。API 可用性不通过偷偷发送生产探测消息来验证。
- 错误说明保留历史、安全下一步、展开技术详情；提供「打开会话」「选择其他模型」「交给小莫」等适用动作，不自动重发用户消息。
- 原生 SwiftUI / SF Symbols，延续现有系统语义色；浅琥珀只表达待处理，操作用明确文字，确保浅深色对比度、键盘焦点、hover 光标与无障碍标签。不引入新的图标或样式库。

验收追加：浅深色离屏截图、长名称与长模型换行、idle / busy / queued / starting / resumed / failed 六态、键盘操作、手选后状态不误报、取消排队、非 tmux 引导。真实交互留给用户验证，不模拟用户前台鼠标键盘。
