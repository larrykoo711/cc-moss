## 目标

配置监听以外，识别已有本地历史中的明确API错误。缺失供应商基线也能发现模型不可用；重复retry不刷通知；可信成功响应才清除故障。不截取终端屏幕，不猜测普通文本，不发送真实API请求。

## Scope

In：安全失败元数据、增量/有界历史扫描、失败去重与恢复、新状态供App消费、隔离回归测试。
Out：读取其他会话正文交给Moss、生产探测、自动重试/重发任务、全自动重开、完整错误日志上传、改为无沙箱。

## 设计与锚点

- `crates/moss-core/src/transcript.rs:42` turn_open处理轮次，不是API成功判据。
- `crates/moss-core/src/settings_json.rs:32` 当前登记hook事件没有API失败独立映射。
- `crates/cc-moss/src/cmd/ls.rs:33` 当前JSON供应商相关只含配置差异与排队状态。
- `notes/provider-model-recovery.md` F45保存脱敏现场；T2.7验证了显式恢复模型，但没有证明错误信号已接入。
- `crates/cc-moss/src/reconcile.rs:43` backfill_names邻近是已有列表扫描入口；`:144` 名称缓存不能复用为错误首次扫描游标。
- `crates/moss-core/src/registry.rs:587` backfill_names增量模式；`:1417` 兼容迁移入口；`transcript.rs:100` scan_back提供64KiB/8MiB单行/32MiB总上限。
- 用独立安全API状态表/访问器，避免扩展进程Status或attention、避免与后端并发修改Slot构造；同slot+session+文件身份+结果位置事务内校验。独立request-scan缓存关联slot/session/path与文件身份，完整行边界推进，缓存写失败不重复报通知。
- 自动监听不能只靠用户再次操作：daemon以低频（约2秒）/单一后台worker调用同一刷新入口，不在100ms循环每轮扫描；无变化文件不读正文，避免阻塞主守护循环。

## 行为口径

- 只认type=assistant且isApiErrorMessage=true的明确错误。模型不可用分类需支持已观测的400 unknown provider for model；其他明确API错误用generic_api，不胡乱归为模型故障。
- 持久化/JSON只含类别、状态码、经校验模型名、时间；不保存或输出原始错误正文、headers、token或工具输出。
- 普通用户retry、tool结果、Stop/finished不清故障。后续可信非错误模型响应清除；synthetic/sidechain消息不得误清。
- 同一故障连续发生只更新同一状态，不重复通知；恢复后再次失败需要重新可见。
- 新session/clear不继承旧session故障；截断/替换历史文件要重核游标。缺历史/坏行fail-open，不把当前健康状态误判成成功。
- 不在每次列表刷新对所有会话扫描32MB；复用增量游标/文件变化缓存，并有单行与总读取上限。

## 契约（2026-10-21 冻结）

App会话JSON新增可选 `api_failure: {kind: model_unavailable|generic_api, status: int|null, model: string|null, at_ms: int|null}`；旧客户端可忽略，无状态时null。无需改变running/working生命周期为interrupted。

## 实施步骤

先解析器单测红→安全有界元数据读取→失败/恢复循环测试红→接入刷新与去重→隔离CLI验证→独立性能/安全评审。不能只测试第一次触发。

## AMEND：扫描缓存与主库锁（2026-10-21）

允许独立私有request-scan.sqlite替代JSON+flock缓存，但禁止每次字节追加写主registry游标，也禁止扫描期间持主registry BEGIN IMMEDIATE。Registry::Drop按total_changes触发registry.changed；缓存频繁写入会制造App自刷新，首次大文件扫描也会阻塞hook。只在新可判定assistant结果时以短主库事务校验/更新API状态，未改变内容只stat，不写主库；序列化锁仅落独立缓存。这是实现细化，验收不弱化。
