## 目标

有一个 `cc-moss daemon` 常驻进程：登录后由 launchd 拉起，被杀或崩溃后自动回来，同一时刻只有一个在跑；`cc-moss daemon status` 能说清它在不在、跑了多久、是哪个版本。它是后面 Moss 会话、Slack、路由的宿主——本任务只交付「活着并被看住」这一层。

## Scope（YAGNI）

**In**：
- `cc-moss daemon run`（前台运行，launchd 调用）、`start` / `stop` / `status [--json]`
- 单实例锁（`<state>/daemon/lock`，`flock`）；状态文件 `<state>/daemon/status.json`（pid、版本、启动时间、心跳）；日志 `<state>/daemon/daemon.log`（1 MiB 轮转，与 `hook.log` 同策略）
- launchd 用户级 LaunchAgent：`~/Library/LaunchAgents/io.github.larrykoo711.cc-moss.daemon.plist`，`RunAtLoad`、`KeepAlive`、`ThrottleInterval` 30、`ProcessType` Background；程序路径用稳定的 cc-moss 路径（与 hook 同一取法 `setup.rs:221`）
- install 布置并 `launchctl bootstrap`；uninstall `bootout` 并删除；版本变化（升级后跑 install）时 `kickstart -k` 换上新二进制
- 通用的「子进程看护」部件：判活（宁漏不误杀）+ 重启阶梯 30s / 2m / 10m / 1h（T2.2 用来看护 Moss），本任务带单测，不接具体子进程
- doctor：报告守护进程状态，没在跑时给出修复命令
- App：设置新页「Moss」只读显示守护进程状态（运行中 / 没在运行 + 一键 `cc-moss daemon start`）

**Out**：
- Moss 会话、Slack、在场检测、路由：T2.2 / T4.x
- root 级 LaunchDaemon：A8，Claude Code 拒绝 root 下 bypass
- App 开机自启（`LoginItem.swift`）：不动，两者独立

## 实施步骤（TDD 序）

1. 红：plist 生成单测（label、ProgramArguments、KeepAlive、日志路径；路径含空格时正确转义）
2. 红：单实例锁——第二个 `daemon run` 立即退出并说明已有实例（`second_daemon_exits`）
3. 红：重启阶梯——连续失败依次 30s、2m、10m、1h，稳定运行 10 分钟后归零（`restart_ladder_backs_off`、`ladder_resets_after_stable_run`）；判活遇到无法判断的错误时当作活着
4. 红：`status --json` 在运行 / 未运行 / 状态文件陈旧（pid 已不在）三种情况
5. 绿：实现 `daemon` 子命令、install / uninstall / doctor 接入、App 页面
6. e2e（临时 HOME，不碰真实 LaunchAgents）：用 `--launchd-dir` 测试开关把 plist 写进临时目录；前台跑 `daemon run`，`kill -9` 后由测试里的看护循环模拟 launchd 重新拉起，`status` 前后一致
7. 真机（用户机，非 e2e）：`launchctl bootstrap` 后 `kill -9`，launchd 拉回；`launchctl print gui/$UID/<label>` 截取

## 风险与回退

- 锁：守护进程被 `kill -9` 时 `flock` 随进程释放，不会留下死锁；状态文件可能陈旧，`status` 以 pid 存活为准
- launchd 在 `ProgramArguments` 路径失效（Homebrew 换版本）时会反复失败：稳定路径用 Homebrew 的 `bin` 链接；doctor 能发现
- 回退：`cc-moss daemon stop` 或 uninstall
