# T2.31-ls-json-speed — `ls --json` 不再逐会话起 `ps`

- Source: 用户 2026-11-22「把 ls --json 慢的问题也修了」（T2.30 排查时发现：单次 1.8 秒、141 KB）
- Evidence: 本机 0.3.14、89 条会话：`ls --json` 实测 1.53–1.57 秒，CPU 仅约 0.28 秒，其余在等子进程。带符号 release 采样：热点为 `provider::model_plan` → `launch_args::argv`（`launch_args.rs:468`）与 `proc::ps_liveness`，都停在 `run_with_timeout`。用 PATH 包装计数：一次 `ls --json` 起 `ps` 186 次，其中 107 次 `-o stat= -o lstart=`（存活检查），79 次 `-o args=`（全部是已结束会话的旧 pid）。连带：`working_directory` 检查的 200 ms 总预算被拖光，59 条会话误报「the working directory could not be checked within the safety budget」。
- arch_level: no
- depends_on: []
- verify_layers: [unit, integration]
- risk: hot-path
- mutations:
  - point: 已结束会话的旧 pid（或被复用的 pid）仍被读启动参数  red: `provider_model_ignores_arguments_of_a_process_the_session_no_longer_runs`
  - point: 内核给的启动时间与 `ps` 写法不一致，已记录的会话全被判死  red: `kernel_start_time_matches_ps`、`start_time_is_written_the_way_ps_writes_it`
  - point: 已回收或僵尸进程被判为活着  red: `kernel_knows_a_reaped_child_is_gone`、`kernel_sees_a_zombie_as_dead`

## 目标

`ls --json`（App 每次刷新都调）不再逐会话起 `ps`：几十条会话也在 0.1 秒内返回，工作目录检查不再因超时误报。

## Scope（YAGNI）

**In**
- `model_plan` 只读仍在运行的会话进程的启动参数：pid 已结束或已被别的进程复用时不读（顺带修正读错进程参数的问题）
- macOS 存活检查先问内核（`proc_pidinfo` / `PROC_PIDTBSDINFO`：状态 + 启动时间），启动时间按 `ps -o lstart=`（`LC_ALL=C TZ=UTC0`，`%c`）原样格式化，与已记录的值逐字可比；内核不答（他人进程等）才退回 `ps`
- 原 `kernel_says_zombie` 并入同一内核查询

**Out**
- 工作目录检查的 200 ms 预算与 64 个目录上限本身（速度恢复后不再触发；上限另议）
- 守护进程其他 `ps` 用法（`parents()` 的 `ps -A`）
