- Source: 2026-11-09 真机：Moss 卡住期间 `moss status` 报 `idle`、Moss 页两条消息一直「发送中…」；用户 G1「卡住也只报告」「给按钮」。
- arch_level: yes
- depends_on: [T2.20]
- risk: ui
- ui: yes
- mutations:
  - 识别函数对 bypass 警告文本返回「没卡住」
  - `activity` 遇到卡住仍报 `idle`
  - 卡住时守护进程向窗格发送按键

## 定标原文

「本次两次 moss agent 消息都处理卡主了」（截图：两条消息下「发送中…」，Moss 头像旁三点在动）。G1：「一律写键，卡住也只报告」「给按钮」。

## 对标卡

沿用 Moss 页现有的状态行与行内提示样式（`MossPage.swift`），不新做视觉体系。卡住时：排队消息的标签不再写「发送中…」，改写「等 Moss 处理一个确认框」这类平实说法；页面顶部一条中性提示说明 Moss 停在哪个确认框上、为什么，配一个「打开 Moss 的窗口」按钮。文案按 `002-menubar/notes/design-voice.md`：说人话、不报错码、不用感叹号。
approved: 2026-11-09 用户 G1「给按钮（推荐）」，沿用现有组件。

## 复用清单

复用守护进程每秒抓窗格的 `accept_trust` 轮询（`moss.rs:1272-1292`）与 `reply.rs` 的窗格文本匹配；复用 App 打开会话终端的既有路径（`attach` / 终端偏好）打开 Moss 的 tmux 窗格；复用 `moss status --json` 的字段扩展方式（`schema` 不升，新增可选字段）。

## 回灌范围

`moss status --json` 新增 `activity: "blocked"` 与 `blocked: {kind, since}`（`kind` ∈ `bypass_warning`、`login`、`unknown_dialog`）；App 的 Moss 页与菜单栏 Moss 状态读这个值；`cc-moss doctor` 报一行。不改 Moss 的启动参数，不替用户点任何选项。

## Success criteria

- [ ] logic：窗格文本识别：真实 bypass 警告文本、登录提示文本判为对应 `kind`；正常输入框、Moss 正在回复、「信任此文件夹」（已有自动处理）不判为卡住。
      verify: `cargo test -p moss-core blocked_dialog_detection`
- [ ] logic：守护进程看到确认框持续 ≥ 5 秒后写卡住标记，确认框消失后清掉；`moss status --json` 报 `activity: "blocked"` 与 `blocked.kind`；全程不向窗格发送按键。
      verify: `cargo test -p cc-moss moss_status_reports_blocked`
- [ ] logic：`cc-moss doctor` 在 Moss 卡住时报一行说明与处理办法，没卡住时不报。
      verify: `cargo test -p cc-moss doctor_reports_moss_blocked`

## 设计

窗格抓取由守护进程做（它已经每秒抓一次用于信任提示），只在 Moss 有待送消息或刚启动的 60 秒内抓，避免常驻开销；卡住标记写在 Moss 家旁的状态目录，`moss status` 读它。出图：`diagrams/moss-blocked.html`（时序：启动 → 抓窗格 → 标记 → status/App → 用户打开窗口处理 → 标记清除）。
